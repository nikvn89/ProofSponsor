# ProofSponsor

**Decentralized sponsorship proof-of-performance on GenLayer.**

ProofSponsor is a full GenLayer dApp for sponsors and creators.

Sponsors define qualitative campaign requirements in natural language. Creators publish their work publicly, prove wallet attribution using a contract-generated ownership marker, and submit the public evidence URL.

GenLayer AI validators then adjudicate whether the submitted deliverable meaningfully fulfilled the sponsorship requirements. Since V4 the verdict also moves money: the sponsor funds a reward pool in GEN, an approved delivery reserves its reward, and the creator withdraws it from the contract.

## How to Try It

1. Connect a wallet. The app switches it to GenLayer Studionet (chain 61999) or adds the network; no Snap is required.
2. Create your own campaign using a **unique campaign ID** and a reward per approved delivery in GEN, then **Fund pool**. The campaign ID namespace is global, so do not use a generic value such as `test`; use something wallet-specific or name-specific.
3. Copy the wallet-specific proof marker generated by the contract and publish it inside a public HTTPS deliverable.
4. Submit that public evidence URL and request adjudication.
5. Verify that accepted state resolves to `APPROVED`, `REJECTED`, or `UNAVAILABLE`. `UNAVAILABLE` preserves the current attempt and exposes **Verify again**.
6. On `APPROVED`, the payout box shows the reserved reward and its claim deadline; the creator wallet sees **Withdraw reward**.

The demo uses a test network; check current StudioNet transaction and deployment fees before testing. Do not fund an unfamiliar wallet or send real assets based on this guide.

## The Problem

Sponsorship agreements often contain qualitative requirements that deterministic smart contracts cannot evaluate.

For example:

> "Publish a meaningful educational article explaining how GenLayer Intelligent Contracts use decentralized AI-validator consensus."

A traditional smart contract can verify an address, payment, timestamp, or exact string, but it cannot reliably determine whether an article actually explains the requested topic or meaningfully satisfies the sponsor's brief.

ProofSponsor turns this subjective fulfillment decision into an onchain adjudication workflow.

## How It Works

```text
Sponsor creates campaign
        ↓
Campaign requirements stored onchain
        ↓
Creator requests wallet-specific proof marker
        ↓
Creator publishes content + marker
        ↓
Creator submits public evidence URL
        ↓
GenLayer AI validators inspect the evidence
        ↓
Decentralized adjudication (run_nondet_unsafe)
        ↓
APPROVED / REJECTED / UNAVAILABLE
        ↓
Result stored onchain
```

## Why GenLayer

ProofSponsor uses GenLayer to resolve the core subjective question:

**Did this creator meaningfully fulfill the sponsorship requirements?**

Deterministic contracts cannot reliably answer this from unstructured public content.

GenLayer Intelligent Contracts allow validators to inspect public evidence and use decentralized AI consensus to determine whether the deliverable semantically satisfies the sponsor's requirements.

The adjudication uses `gl.vm.run_nondet_unsafe` with a leader-validator pattern:

- **Leader** fetches the public evidence, verifies the wallet attribution marker, and prompts the AI to evaluate semantic fulfillment against the campaign requirements.
- **Validators** independently repeat the same evaluation and confirm agreement with the leader verdict.

This makes the adjudication result usable by other onchain systems such as:

- sponsorship payouts
- escrow release
- creator reputation
- campaign completion records
- automated reward systems

## Creator Ownership Proof

ProofSponsor generates a wallet-specific marker:

```text
SPONSORJUDGE_PROOF:<creator-wallet>
```

Example:

```text
SPONSORJUDGE_PROOF:0x146e44881d35814ba582d265af5b97ef2695ec8e
```

The creator places this marker inside the public deliverable.

Validators therefore verify both:

1. whether the content satisfies the sponsorship brief
2. whether the public evidence is associated with the wallet submitting it

## Honest Limitation

ProofSponsor verifies only what is observable in the submitted public evidence. The wallet-specific marker proves that the marker was published at the submitted URL and matches the wallet making the submission; it does **not** prove a person's real-world identity, legal ownership of the surrounding content, authorship, or the real-world quality/value of the work.

An `APPROVED` result means only that GenLayer validators found the accessible evidence to meaningfully satisfy the campaign requirements and to contain the expected wallet attribution marker under this contract's rubric. It is not a legal certification, identity proof, or guarantee of off-chain performance.

## Security Design

- **Wallet-specific attribution:** `SPONSORJUDGE_PROOF:<wallet>`
- **Public evidence ownership:** evidence must be associated with the submitting creator
- **Canonical URL identity:** common tracking, fragment, hostname-case, `www`, and trailing-slash variants share one attempt/claim key
- **Anti-replay:** approved canonical evidence is claimed per campaign
- **Retrieval-safe adjudication:** inaccessible or empty evidence returns `UNAVAILABLE`, preserves the attempt, and can be verified again; marker-missing evidence remains `REJECTED`
- **Bounded recovery:** five consecutive retrieval failures close the preserved attempt as `REJECTED`
- **Prompt-injection fencing:** the evidence page and the creator's description are both fenced as untrusted content; every fence marker is stripped in any letter case until none remains
- **Funded rewards:** an approval reserves the reward from the sponsor's pool; reserved GEN can only go to that creator, or back to the pool after the 30-day claim window
- **No dodging a verdict:** closing a campaign stops new submissions only; deliveries already submitted are still judged and paid
- **Reclaim last:** the sponsor reclaims only unreserved GEN, only after closing, and only when no delivery awaits a verdict and no approved reward waits for funds
- **Marker check before truncation:** attribution is checked against the full evidence before prompt-size truncation
- **Semantic evaluation:** validators evaluate fulfillment rather than keyword presence alone
- **Campaign lifecycle:** closed campaigns cannot accept new submissions or revisions
- **Onchain persistence:** adjudication results are stored onchain

## Frontend Reliability

ProofSponsor reads GenLayer `accepted` state when loading contract data.

A write is reported as done only when the leader receipt says `execution_result = SUCCESS` and consensus has reached `ACCEPTED`, `READY_TO_FINALIZE` or `FINALIZED`. A leader error is shown as the contract's own revert sentence; a missing result is shown as "submitted — confirmation delayed", never as success. Wallet writes switch the wallet to StudioNet with `wallet_switchEthereumChain` (adding the network on error 4902), so plain MetaMask works without the GenLayer Snap.

AI adjudication is asynchronous. After `judge_content` returns a transaction hash, the frontend polls submission status with backoff until the contract reports:

```text
APPROVED
```

or:

```text
REJECTED
```

or:

```text
UNAVAILABLE
```

`UNAVAILABLE` is a retrieval state, not a negative content verdict. The UI shows the preserved attempt and retry counter, and lets a reviewer call `judge_content` again after the page recovers.

Transient RPC or rate-limit errors during polling do not automatically mark the adjudication as failed.

The frontend also rejects evidence URL forms known to be unreliable for validator rendering:

- `raw.githubusercontent.com`
- GitHub `/blob/` URLs

Creators should provide a publicly accessible HTTPS webpage that GenLayer validators can render.

## V4: the verdict pays

V3 decided whether a delivery met the brief, but payment happened somewhere else, on trust. `contracts/ProofSponsorV4.py` holds the sponsor's GEN:

- `create_campaign` takes a reward per approved delivery; `fund_campaign` (payable, sponsor only) fills the pool and can be topped up at any time, even after closing.
- An `APPROVED` verdict reserves the reward if the pool covers it (`RESERVED`), or records `UNDERFUNDED`. `reserve_underfunded` lets anyone reserve it once the pool covers it.
- `withdraw_reward` pays the creator once. A reservation is held for 30 days from the transaction date that made it; afterwards anyone may call `release_expired_reward` to return it to the pool. The creator can still withdraw until someone does.
- `reclaim_unused` returns only unreserved GEN to the sponsor, and only after the campaign is closed, no delivery awaits a verdict, and no approved reward is waiting for funds.
- `judge_content` now works on a closed campaign, so closing cannot be used to avoid a verdict (in V3 it reverted and left the delivery stuck).
- The creator description is fenced like the evidence page, and the fence strip is case-insensitive and repeated to a fixed point (V3 removed two exact-case markers once).
- Amount views (`get_campaign_treasury`, `get_payout`) return wei as decimal strings, so values above 2^53 stay exact.

The app adds a reward field on create, a treasury panel (pool, reserved, available, fund, close/reopen, reclaim with the reason it is blocked), and a payout box on each delivery (claim deadline and days left, **Withdraw reward**, **Reserve reward now**, **Release expired reward**). The public review page shows the reward record.

Tests: 51 GenVM Direct Mode tests run the V4 contract inside the real py-genlayer v0.2.16 SDK (three of them document the V3 weaknesses on the V3 contract), and a 45-mutant matrix must be fully killed. See [TESTING.md](./TESTING.md).

## V3: retrieval failures preserve the attempt

`contracts/ProofSponsorV3.py` separates evidence retrieval from semantic adjudication. A render exception, `None`, or blank response becomes `UNAVAILABLE`; it does not consume a second attempt and it does not claim the content failed the sponsor brief. When the page recovers, **Verify again** runs `judge_content` against the same attempt. Five consecutive retrieval failures close that attempt as `REJECTED` with an explicit retrieval reason.

V3 also canonicalizes common URL variants before storing attempted/claimed keys. It removes fragments and known tracking parameters, normalizes scheme/host/`www`, preserves path case, and keeps meaningful query parameters such as `?v=`. This is best-effort URL identity, not content identity; see [SECURITY.md](./SECURITY.md) for the remaining limitation.

The load-bearing StudioNet recovery run is complete. Campaign `v3-recovery-250925-01` first reached `UNAVAILABLE` while its evidence page returned 404, preserving **Attempt 1 of 3** with retrieval retry `1 of 5`. After the same URL was published, a second `judge_content` call reached `APPROVED` without creating another attempt. See [RUNTIME_EVIDENCE.md](./RUNTIME_EVIDENCE.md) and the retained [`docs/evidence`](./docs/evidence/README.md) screenshots. Additional deterministic URL-identity and authorization cases are covered by local tests and are explicitly distinguished from live StudioNet evidence.

## V2: revise a rejected delivery

The previous contract generation is in `contracts/ProofSponsorV2.py`, separate from the already deployed V1. On V1 a creator's first submission is final even if rejected. In V2 the submitting creator can call `revise_rejected_content` with a different public HTTPS URL and description after a `REJECTED` result. This creates another `SUBMITTED` attempt; anyone may request a fresh `judge_content` adjudication. The contract keeps the original rejected evidence and reason, plus every later attempt, onchain. Only three attempts total are allowed. `APPROVED` and pending submissions cannot be revised; closed campaigns reject revisions.

V2 is deployed as a separate contract because V1 has no documented upgrader configured. There is no automatic migration of V1 campaigns or submissions. The following is the historical verified V2 configuration, not the V3 production configuration:
